# JWT (JSON Web Tokens)

JWT(JSON Web Token)는 서버와 클라이언트가 **인증/인가 정보를 안전하게 주고받기 위한 토큰 형식**입니다.  
로그인 후 매 요청마다 세션을 조회하는 방식 대신, 토큰 자체에 필요한 정보를 담아 인증 상태를 확인할 수 있습니다.

## JWT를 왜 사용할까?

전통적인 세션 기반 인증은 서버 메모리(또는 세션 저장소)에 상태를 보관합니다.  
반면 JWT는 기본적으로 **Stateless**하게 동작하므로, 다음과 같은 장점이 있습니다.

- 서버 확장(Scale-out) 시 세션 동기화 부담이 줄어듭니다.
- API 서버, 모바일, SPA 등 다양한 클라이언트와 궁합이 좋습니다.
- 표준(JSON + 서명) 기반이라 언어/프레임워크 간 호환성이 높습니다.

다만 JWT는 만능이 아니며, 사용 방식이 잘못되면 보안 리스크가 커질 수 있습니다.  
그래서 "구조를 이해하고 제한점을 전제로 설계"하는 것이 중요합니다.

## JWT 구조: `Header.Payload.Signature`

JWT는 점(`.`)으로 구분된 3개 파트로 구성됩니다.

1. Header: 토큰 타입, 서명 알고리즘(`alg`) 정보
2. Payload: 사용자 식별자, 권한, 만료시간 등 클레임(Claim)
3. Signature: 위 두 값을 비밀키/개인키로 서명한 값

핵심은 **Payload가 암호화가 아니라 인코딩(Base64URL)된 정보**라는 점입니다.  
즉, 민감정보(비밀번호, 주민번호 등)는 절대 넣으면 안 됩니다.

## Claim(클레임) 이해하기

Payload에는 클레임이 들어가며 보통 아래 3종류로 나뉩니다.

- Registered Claim: 표준 필드 (`iss`, `sub`, `aud`, `exp`, `nbf`, `iat`, `jti`)
- Public Claim: 협의된 공개 이름의 사용자 정의 필드
- Private Claim: 서비스 내부에서만 쓰는 커스텀 필드

실무에서는 보통 아래 필드가 자주 사용됩니다.

- `sub`: 사용자 고유 식별자
- `role` 또는 `scope`: 권한 정보
- `exp`: 만료 시각
- `iat`: 발급 시각
- `jti`: 토큰 고유 ID(로그아웃/블랙리스트 처리 시 유용)

## 인증 흐름(Access Token + Refresh Token)

일반적인 토큰 기반 인증 흐름은 다음과 같습니다.

1. 사용자가 로그인 성공
2. 서버가 Access Token(짧은 수명)과 Refresh Token(긴 수명) 발급
3. 클라이언트가 Access Token으로 API 호출
4. Access Token 만료 시 Refresh Token으로 재발급 요청
5. 서버가 Refresh Token 검증 후 새 Access Token 발급

이 구조를 쓰는 이유는 보안과 UX의 균형 때문입니다.  
Access Token 수명을 짧게 두면 탈취 시 피해를 제한할 수 있고, Refresh Token으로 재로그인 빈도를 줄일 수 있습니다.

## JWT 사용 시 자주 하는 실수

- 토큰에 민감정보를 저장함
- 만료시간(`exp`)을 과도하게 길게 설정함
- 로컬스토리지에 장기 토큰을 저장하고 XSS를 방치함
- `alg` 검증을 느슨하게 처리함
- 로그아웃/강제만료(폐기) 전략 없이 운영함

## 보안 모범 사례

- Access Token은 짧게(예: 10~30분), Refresh Token은 회전(Rotation) 정책 적용
- 웹 환경에서는 가능한 `HttpOnly + Secure + SameSite` 쿠키 사용 검토
- 서명 키는 환경변수/비밀관리 시스템으로 분리하고 정기 교체
- 서버에서 `iss`, `aud`, `exp`, `nbf`, 서명 알고리즘을 엄격 검증
- 권한 변경/로그아웃을 고려해 `jti` 기반 블랙리스트 또는 버전 관리 도입

## JWT는 언제 적합하고, 언제 아닐까?

JWT가 적합한 경우:

- 다수의 API 서버를 수평 확장해야 하는 환경
- 모바일/웹/외부 클라이언트가 함께 사용하는 인증 체계
- OAuth2/OIDC 기반 토큰 인증 연동

세션이 더 단순한 경우:

- 단일 서버 중심의 전통적 웹앱
- 즉시 무효화 요구가 매우 강하고 토큰 관리 복잡도를 피하고 싶은 경우

## 마무리

JWT는 "세션을 대체하는 기술"이라기보다,  
**분산 환경에서 인증 정보를 다루기 위한 표준 토큰 포맷**입니다.

핵심은 다음 한 줄로 정리됩니다.

`JWT 자체보다, 수명/저장 위치/검증 규칙/폐기 전략을 어떻게 설계하느냐가 보안을 결정한다.`
